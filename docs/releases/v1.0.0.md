# boost-html v1.0.0 — draft release notes

> **Draft — not approved. Do not publish.**

**Status:** release candidate preparation only. The package version remains
`0.1.0`; this document is not a release announcement. No npm publish, GitHub
Release, tag, or version bump has been performed.

## Summary

The planned first stable release provides progressive enhancement for
multi-page HTML applications using same-origin Fetch navigation, native DOM
replacement, browser history, scroll/focus restoration, accessible page
announcements, optional prefetch, and an opt-in in-memory navigation cache.

## Highlights

- Automatic root-entry initialization and side-effect-free `boost-html/core`
  entry for manual lifecycle management.
- Delegated same-origin link and form handling with native browser behavior
  preserved for ineligible links/forms.
- Native History API integration, back/forward restoration, hash scrolling,
  focus management, and polite live-region announcements.
- Native DOM replacement by default, with optional synchronous morph/swap
  adapters.
- Zero mandatory runtime dependencies and built-in progress UI.
- Optional prefetch and navigation cache, both disabled by default.
- ESM, CommonJS, browser IIFE, and TypeScript declaration outputs.

## Important behavior changes from the 0.1.x development line

- Response scripts are never automatically executed. `executeScripts` is
  deprecated and ignored; explicit script processing requires `scriptHandler`.
- POST forms default to `application/x-www-form-urlencoded` unless `enctype`
  requests multipart or text/plain.
- Failed non-idempotent forms are not automatically re-submitted. The
  `fallbackToNativeForm` option is an explicit opt-in with duplicate-submission
  risk.
- Missing or non-HTML response content types are rejected.
- Programmatic navigation and final redirect URLs must remain same-origin
  HTTP(S).
- Navigation responses are limited to 2 MiB by default.
- Response filtering, CSP nonce support, Trusted Types integration, and the
  security model are documented in `docs/SECURITY.md`.

## Browser and test coverage

The release preparation suite covers Chromium, Firefox, and WebKit. Strict
Trusted Types enforcement is tested in Chromium. The local validation report
is maintained in `docs/RELEASE_READINESS.md`; remote GitHub Actions must pass
before this draft can become release notes.

## Known limitations

- The active-content filter is defense in depth, not a general-purpose HTML
  sanitizer.
- Custom elements, DOM clobbering in host application code, CSRF, authorization,
  and correctness of server `Cache-Control: public` directives remain host/server
  responsibilities.
- The navigation cache cannot inspect HttpOnly cookies.
- The 5 KiB core ESM gzip goal remains open; current size limits are regression
  ceilings, not proof the goal has been achieved.
- Long-duration memory soak testing and remote CI validation remain outstanding.
